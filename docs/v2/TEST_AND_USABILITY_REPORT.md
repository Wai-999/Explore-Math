## What the browser suite establishes

New end-to-end cases follow Discover → vectors, manipulate arrows/columns/numeric input, load both worked examples, move through justified proof steps, change explanation depth, solve a new numeric/rule case, use a hint on another case, reload, snapshot, and export dated evidence. All four concepts are exercised. Separate cases cover undefined zero-gap/zero-direction states, jump/cusp limits, saddle/overshoot, protected legacy migration, mixed Prediction Studio/project/journey backups, rejected future imports and Back/Forward navigation.

The builder suite tests a solved vector goal, duplicate/save/rename/reset, JSON round trip, corrupt/oversized/future-schema rejection, report content, generated standalone Python parity, cost optimum including boundary candidates and phone layout. Independent objective work and explanation self-checks are distinct records.

Keyboard-only test actions use real key input: Tab, reverse Tab, Enter/Space and typed numeric answers, without programmatic focus or a mouse. It completes vector and derivative practice plus the applied navigation goal and a saved project in forced no-WebGL mode. On macOS WebKit, **Option+Tab** traverses buttons/links when the platform's ordinary Tab traversal skips them; this native convention is explained in the lesson guide. The test can reverse direction when headless Firefox keeps focus on the last page link. This is browser keyboard coverage, not a human assistive-technology study.

Axe scans all four learning lenses for each R1 concept in light/dark, plus builder and inherited destinations; no serious/critical violations in the tested states. Width checks cover 320, 375, 768 and 1280 px. Tests also retain reduced-motion, context-loss fallback and existing mission coverage. Automated pointer dragging checks both vector and matrix-plane tips; numeric inputs remain equivalent. Actual physical touch remains untested.

## Performance and bundle impact

Production chunks (decimal kB, gzip): ThreeStage **953.78 / 254.15**, versus baseline **952.44 / 253.75**. Increase is about 1.34 kB raw / 0.40 kB gzip. ConceptJourney is about **52.98 / 17.11**; ProjectBuilder **29.71 / 10.06**; shared education **22.40 / 8.56**. Exact hashes may change with formatting/version metadata. No new runtime dependency was added. Three.js remains lazy; the default vector and matrix-plane visits were checked to avoid its request. The optional volume view mounts/unmounts the existing engine; geometry cleanup remains in the renderer.

Measured acceptance budgets for this R1 review: ThreeStage ≤260 kB gzip, guided component ≤20 kB gzip, builder ≤12 kB gzip, and no ThreeStage request until a 3D activity is opened. Current measurements meet them; these are review budgets, not new CI size assertions. Keep performance work tied to measured regressions instead of adding continuous effects.

One unthrottled local production navigation per route, October 26: DOMContentLoaded Discover **17.2 ms**, vectors **6.0 ms**, matrices **4.4 ms**, derivatives **5.7 ms**, gradients **5.0 ms**, builder **8.5 ms**. The scripted navigation/H1/optional guide-dismissal sequence took roughly 354–1161 ms across these samples. Localhost, warmed shared browser cache, concurrent QA and automation make these unsuitable as public-site or low-end-device speed promises. No FPS, battery or learning improvement is inferred. Baseline public/dev timing is not a directly comparable before/after production benchmark.

## Owner-arranged novice and educator review

Request **3–5 real beginner volunteers** via the owner; do not contact or invent participants. With consent, record only necessary qualitative notes, no private data in the app repository. Each session should use a clean browser profile, one vector or derivative path, and an unfamiliar new case. Suggested 15–20 minute protocol:

1. Cold start: “Find how to reach the target with wind” or “Explain the slope of x².” Observe first successful input, time/assistance and undefined terms without coaching.
2. Ask the learner to connect one arrow/point change to coordinates and the corresponding formula, then explain one derivation step in their words. Record the actual statement and any help.
3. Give a fresh seeded case without a hint or solution. Compare the objective answer and a short reasoning rubric; record misconceptions and equivalent explanations without a fabricated AI score.
4. Ask them to create, solve and save a small project, export it, and explain one assumption/limitation. Check where they confuse units, model and real-world decision.
5. Invite a later fresh problem, recording elapsed time, help and transfer; a seven-day suggested revisit is a convention, not a validated retention schedule.

Have an independent mathematics educator check the four base derivations, mode-specific assumptions, worked arithmetic, determinant/length distinction, function-versus-derivative limits and saddle/step guarantees. A screen-reader user should navigate the same core tasks; physical phone users should test drag, pinch/orbit, controls and recovery. Record PASS/FAIL findings only after these sessions occur. Small samples inform design qualitatively, not statistical educational effectiveness. Correct material findings before the production-release decision.
